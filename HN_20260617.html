📄 สรุปเนื้อหาบทความ

ผู้เขียนแชร์ประสบการณ์ตรงหลังจากได้รับข้อความเสนอโอกาสทางวิชาชีพจากผู้สรรหาบุคลากร (Recruiter) ของสตาร์ทอัปคริปโตรายหนึ่งบน LinkedIn โดยขอให้ช่วยตรวจสอบปัญหาเกี่ยวกับโมดูล Node ที่หมดอายุ (Deprecated) ในคลังเก็บโค้ด (GitHub Repository) สาธารณะของพวกเขา แต่เมื่อผู้เขียนทำการตรวจสอบก็พบความผิดปกติที่อันตรายอย่างยิ่ง:

  • การใช้สภาพแวดล้อมที่ปลอดภัยในการตรวจสอบ: ผู้เขียนไม่ได้ทำการโคลนและติดตั้งโปรเจกต์ลงในเครื่องคอมพิวเตอร์ส่วนตัวโดยตรง แต่เลือกใช้บริการ VPS แบบใช้แล้วทิ้ง (Throwaway VPS) ของ Hetzner และให้เอเจนต์ AI ที่เปิดสิทธิ์อ่านอย่างเดียว (Read-only Agent) ช่วยตรวจสอบแทน
  • กับดักสคริปต์ Backdoor: โค้ดพรางตัวในลักษณะระบบทดสอบ (Test Suite) ยาวประมาณ 250 บรรทัดที่ไฟล์ app/test/index.js ซึ่งจะทำงานทันทีที่มีการรัน npm install ผ่านการทำงานของสคริปต์ prepare ในไฟล์ package.json
  • การทำงานของมัลแวร์: สคริปต์จะทำการประกอบ URL จากเศษเสี้ยวข้อความที่ซ่อนไว้เพื่อเรียกไปที่ https://rest-icon-handler.store/icons/77 และรันคำสั่งใดๆ ก็ตามที่เซิร์ฟเวอร์ปลายทางส่งกลับมา (Arbitrary Remote Code Execution)
  • การแอบอ้างตัวตนอย่างแนบเนียน: คณะผู้โจมตีแอบอ้างตัวตนของนักพัฒนาที่มีชื่อเสียงจริงในการ Commit โค้ดถึง 39 ครั้ง และใช้บัญชีผู้สรรหาบุคลากรที่แอบอ้างโปรไฟล์ของนักข่าวสายศิลปะชื่อดังเพื่อสร้างความน่าเชื่อถือ

  • การใช้เทคโนโลยีช่วยคัดกรอง: ผู้ใช้ชื่นชมแนวคิดในการใช้ AI แบบอ่านอย่างเดียวช่วยรีวิวโค้ดก่อนติดตั้ง ซึ่งให้ผลลัพธ์ที่รวดเร็วและแม่นยำกว่าการนั่งไล่ตรวจทีละบรรทัดด้วยตนเอง
  • ข้อเสนอแนะในการป้องกัน: แนะนำให้เปลี่ยนมารันคำสั่งสร้างและติดตั้งโปรเจกต์ (เช่น npm, docker) ภายใต้เทคโนโลยี Docker container หรือระบบเวอร์ชวลไลเซชัน (Virtualization Framework) ที่จำกัดการเข้าถึงโฟลเดอร์ในเครื่องจริง

  • การหลีกเลี่ยงการถูกยัดเยียด AI จากผู้ผลิต (AI Bloatware): สมาชิกแสดงความกังวลต่อนโยบายของ Google ใน Android 17 ที่ประกาศจะเปลี่ยนระบบปฏิบัติการให้เป็นระบบอัจฉริยะ (Intelligence System) ที่ควบรวม AI เข้ากับตัวเครื่องอย่างแนบแน่น ซึ่งทำให้นักพัฒนาที่รักความเป็นส่วนตัวเห็นพ้องว่า GrapheneOS จะยิ่งกลายมาเป็นทางเลือกสำคัญในการปิดกั้นการสอดส่องและเก็บข้อมูลดังกล่าว

💬 สรุปประเด็นเสวนาในกระทู้

หัวข้อนี้จุดชนวนการอภิปรายอย่างกว้างขวางใน Hacker News เกี่ยวกับเศรษฐศาสตร์ยุคหลังการทำงานและการแทนที่มนุษย์ด้วยเครื่องจักร โดยสรุปประเด็นหลักได้ดังนี้ครับ:

  • ทฤษฎีการแบ่งแยกทวีปแห่งปัญญา (AI Island vs. Elsewhere): สมาชิกได้จำลองสถานการณ์สมมติหากโลกถูกแยกเป็นดินแดน AI ที่มีแต่เซิร์ฟเวอร์ประมวลผลกับฝั่งมนุษย์ โดยเกิดการวิเคราะห์ว่ากลุ่ม AI จะต้องการสิ่งใดมาแลกเปลี่ยนกับบริการทางซอฟต์แวร์ และหุ่นยนต์ในฝั่ง AI จะต้องมีความสามารถผลิตอาหารและสินค้าทดแทนแรงงานทางกายภาพทั้งหมดได้อย่างสมบูรณ์
  • ความเป็นจริงของระบบอัตโนมัติในภาคเกษตรกรรม: นักพัฒนาเปรียบเทียบว่า ปัจจุบันแรงงานภาคเกษตรในสหรัฐฯ ลดลงจาก 50% เหลือเพียง 1% เนื่องจากเครื่องจักรและการทำงานกึ่งอัตโนมัติ ซึ่งไม่ใช่เรื่องเพ้อฝันที่วันหนึ่ง AI จะสามารถจัดการระบบจัดการฟาร์ม ค้นหาพื้นที่เพาะปลูก และควบคุมเครื่องจักรได้โดยปราศจากการแทรกแซงของมนุษย์
  • ความเสี่ยงเรื่องความเหลื่อมล้ำและสภาวะการสะสมความมั่งคั่ง: มีความกังวลว่าความก้าวหน้าของระบบเศรษฐกิจแบบไร้มนุษย์จะไม่นำไปสู่สภาวะหลุดพ้นจากความขาดแคลน (Post-scarcity) สำหรับทุกคน แต่จะเอื้อให้กลุ่มทุนผู้ครอบครองเทคโนโลยีและที่ดินสามารถกอบโกยทรัพยากรทั้งหมดไว้เพียงฝ่ายเดียว ขณะที่ประชากรส่วนใหญ่ต้องเผชิญกับวิกฤตการขาดแคลนงานและรายได้
  • ประเด็นขำขันเชิงปรัชญาต่อระบบการค้า: สมาชิกบางส่วนเสนอความเห็นเชิงตลกแกมเสียดสีว่า สุดท้ายแล้วระบบเศรษฐกิจใหม่อาจมีเพียงแค่ปัญญาประดิษฐ์ระดับสูงของบริษัทเทคโนโลยีต่างๆ ทำการซื้อขายหุ้นและแลกเปลี่ยนข้อมูลเพื่อปั่นยอดตัวเลขและเสิร์ฟโดปามีนให้แก่ผู้สร้างของตนเองเท่านั้น

Correlated randomness in Slay the Spire 2

การค้นพบช่องโหว่ความสัมพันธ์เชิงเส้นของระบบสุ่ม (Correlated RNG) ในเกม Slay the Spire 2 ส่งผลให้ผู้เล่นสามารถทำนายผลการสุ่มไอเทมและคำสาปในเกมได้อย่างแม่นยำ

📄 สรุปเนื้อหาบทความ

บทความวิเคราะห์เชิงลึกเกี่ยวกับข้อผิดพลาดในระบบสุ่ม (Pseudorandom Number Generator) ของเกมการ์ดชื่อดังยอดนิยมอย่าง Slay the Spire 2 รุ่นทดสอบเบต้า (v0.107.0) ซึ่งสร้างความเชื่อมโยงที่คาดเดาได้ของผลลัพธ์สุ่มในเกม โดยมีรายละเอียดดังนี้ครับ:

  • ปรากฏการณ์สุ่มที่ไม่เป็นอิสระต่อกัน (CRNG): ผู้เล่นพบว่าการเลือกไอเทมเริ่มต้นบางประเภทส่งผลให้มีโอกาสได้รับคำสาปประเภทเดิมซ้ำๆ เช่น มีโอกาสได้รับคำสาปหนี้สิน (Debt) สูงถึง 54% ในด่านแรก และอัตราการดร็อปยาน้ำ (Potion) ระหว่างสองด่านแรกมีความแตกต่างกันอย่างผิดปกติ (76% เทียบกับ 4%)
  • สาเหตุจากการใช้ System.Random ใน C#: แม้ผู้พัฒนาจะพยายามแก้ไขความบกพร่องจากภาคแรกด้วยการสุ่มแฮชเมล็ดพันธุ์ (Seed hashing) แยกสําหรับแต่ละเหตุการณ์ แต่เมื่อนำค่าเมล็ดพันธุ์เหล่านั้นไปใช้กับฟังก์ชันสุ่มมาตรฐาน System.Random ของ C# ซึ่งมีอัลกอริทึมสุ่มที่เป็นแนวเชิงเส้น (Linear in starting seed) ทำให้ผลลัพธ์การสุ่มช่วงต้นของ RNG แต่ละตัวมีทิศทางสัมพันธ์กันอย่างหลีกเลี่ยงไม่ได้
  • ผลกระทบต่อรูปแบบการเล่นเกม (Gameplay Impact): ความบกพร่องนี้ส่งผลเสียต่อความหลากหลายในการเล่นเกม ทำให้สุ่มพบไอเทมระดับดีหรือการ์ดหายากมีแนวโน้มเอียงไปในทิศทางที่แน่นอนตามเส้นทางเดินและชนิดของแผนที่ที่เลือก

💬 สรุปประเด็นเสวนาในกระทู้

  • การป้องกันการโกงผลลัพธ์สุ่มด้วยการโหลดเซฟ (Anti-Savescumming Design): นักพัฒนาถกเถียงถึงความจำเป็นของการแยกชุดสุ่ม (RNG engines) ออกจากกันในแต่ละเหตุการณ์ เพื่อป้องกันผู้เล่นใช้ทริกย้อนเวลากลับไปเล่นการต่อสู้เดิมใหม่ (Savescumming) โดยปรับเปลี่ยนการกระทำบางอย่างเพื่อให้ได้ผลรางวัลการ์ดหรือของรางวัลหลังจบไฟต์ที่ดีขึ้น

  • กลไกการกู้คืนสถานะเกมของทีมพัฒนา: เผยให้เห็นเทคนิคที่น่าสนใจว่า เกมบันทึกค่าสถานะด้วยการจัดเก็บจำนวนครั้งที่มีการเรียกใช้ตัวสุ่มในแต่ละสัญญะ และเมื่อผู้เล่นทำการโหลดไฟล์เซฟกลับมาใหม่ ระบบจะทำการสั่งรันสุ่มทิ้งตามจำนวนครั้งดังกล่าวเพื่อให้เข้าสู่สถานะสุ่มเดียวกันกับก่อนปิดเกม

📄 สรุปเนื้อหาบทความ

สรุปเนื้อหาบทความ: จากประสบการณ์การสัมภาษณ์งานของนักเขียนพบว่า ปัจจุบันบริษัทเทคโนโลยีเกือบทั้งหมดหันมาใช้งาน Kubernetes (K8s) เป็นมาตรฐาน แม้แต่ในสตาร์ทอัพขนาดเล็กที่มีพนักงานเพียง 10 คนและไม่มีความจำเป็นต้องรองรับผู้ใช้จำนวนมหาศาล

  • ความสม่ำเสมอในการจัดวางระบบ (Uniformity): การใช้ K8s ช่วยขจัดปัญหาบริการแต่ละตัวทำงานด้วยวิธีหรือชุดคำสั่งที่แตกต่างกัน (เช่น บางบริการใช้สคริปต์โบราณบน VM ขณะที่อีกบริการใช้ Docker Compose) ทำให้ทุกบริการมีรูปแบบการใช้งานและติดตั้งที่เหมือนกันทั้งหมด
  • การถ่ายทอดและจัดจ้างแรงงานได้ง่าย (Shared Knowledge): รูปแบบการเขียนคอนฟิกด้วยไฟล์ YAML หรือ Helm Chart กลายเป็นภาษากลางที่วิศวกรทุกคนเข้าใจร่วมกัน ช่วยให้พนักงานใหม่สามารถทำความเข้าใจโครงสร้างระบบได้ในเวลาไม่นาน และขจัดปัญหาความรู้ผูกขาดอยู่กับตัวบุคคล
  • การตรวจสอบความถูกต้องและข้อกำหนดทางกฎหมาย (Traceability): กระบวนการ GitOps (เช่น FluxCD หรือ ArgoCD) ทำงานร่วมกับ K8s ได้เป็นอย่างดี ทำให้ทุกการเปลี่ยนแปลงระบบต้องผ่านการอนุมัติและบันทึกประวัติการพัฒนา ซึ่งมีส่วนช่วยให้บริษัทสามารถผ่านการตรวจสอบมาตรฐานความปลอดภัย เช่น ISO ได้อย่างง่ายดาย
  • ข้อเสนอแนะในการเริ่มต้น: ผู้เขียนแนะนำว่าในช่วงแรกเริ่มของบริษัท ควรเน้นพัฒนาผลิตภัณฑ์บน VPS หรือวิธีการที่ง่ายก่อนการใช้ระบบที่ซับซ้อนอย่าง K8s เพื่อหลีกเลี่ยงการเสียเวลากับการดีบักปัญหาโครงสร้างพื้นฐาน

  • วิธีการทำงาน: Bash มีความสามารถในการเปิดซ็อกเก็ต TCP ได้เองโดยการอ้างอิงตำแหน่งเสมือน /dev/tcp/host/port ซึ่งไม่ใช่ไฟล์จริงบนระบบดิสก์ แต่เป็นการจัดการภายในของเชลล์เอง
  • รูปแบบการส่งคำขอ: ผู้ใช้สามารถเปิดสิทธิ์อ่านเขียนบน File Descriptor ด้วยคำสั่ง exec 3<>/dev/tcp/host/port จากนั้นเขียนคำสั่งร้องขอ HTTP ดิบ (Raw HTTP request) ลงไป และอ่านค่าผลลัพธ์กลับมาด้วยคำสั่งเชลล์ธรรมดา
  • ข้อจำกัดสำคัญ: วิธีการนี้ไม่มีคุณสมบัติของเว็บบราวเซอร์ เช่น การสนับสนุนรหัสความปลอดภัย (TLS/HTTPS) การแปลงข้อมูลย่อส่วน (Compression) หรือการจัดการการเปลี่ยนเส้นทาง (Redirects) และจำเป็นต้องระบุ Header Connection: close เพื่อป้องกันไม่ให้โปรแกรมค้างขณะรอผลลัพธ์

📄 สรุปเนื้อหาบทความ

สรุปเนื้อหาบทความ: บทความเตือนนักพัฒนาให้หยุดใช้ JWT (JSON Web Tokens) ในการคงสถานะการล็อกอินของผู้ใช้ (User Session) บนเบราว์เซอร์ โดยชี้ว่า JWT ไม่ได้ถูกออกแบบมาเพื่อสิ่งนี้ และการใช้เทคโนโลยีเซสชันคุกกี้ปกติมีความปลอดภัยและเหมาะสมมากกว่า

  • อายุการใช้งานและ State: มาตรฐาน JWT ออกแบบมาสำหรับโทเค็นอายุสั้นมาก (~5 นาทีหรือน้อยกว่า) การทำระบบเซสชันที่ปลอดภัยแบบไร้สถานะ (Stateless) บนเบราว์เซอร์ทำได้ยากมาก และหากสุดท้ายต้องเก็บสถานะเพื่อยกเลิกโทเค็น ก็ควรหันไปใช้ Session Store ตั้งแต่แรก
  • ความเปราะบางของมาตรฐาน: มาตรฐานดั้งเดิมของ JWT ถูกวิจารณ์โดยผู้เชี่ยวชาญด้านความปลอดภัยว่ามีความซับซ้อนเกินไปและเอื้อให้เกิดการตั้งค่าที่ผิดพลาดได้ง่าย (เช่น อัลกอริทึม 'none' หรือการปลอมแปลงคีย์)
  • กรณีขององค์กรใหญ่: บริษัทอย่าง Google ไม่ได้ใช้ JWT สำหรับเซสชันในเบราว์เซอร์ แต่ใช้คุกกี้ปกติ ส่วน JWT จะถูกใช้เฉพาะในการส่งผ่านข้อมูลเพื่อล็อกอินข้ามระบบ (Single Sign-On - SSO) เท่านั้น
  • ทางเลือกอื่น: แนะนำโปรโตคอล PASETO แทนหากต้องการส่งข้อมูลโทเค็นอายุสั้นที่ลงลายมือชื่อแบบปลอดภัย

💬 สรุปประเด็นเสวนาในกระทู้

ประเด็นดราม่าและการถกเถียงใน Hacker News เกี่ยวกับความเหมาะสมในการใช้งาน JWT แบ่งออกเป็นสองฝั่งอย่างชัดเจน:

  • การยอมรับว่าไม่เหมาะกับเบราว์เซอร์เซสชัน: นักพัฒนาส่วนใหญ่เห็นพ้องกับบทความว่าการเก็บ JWT ไว้ใน localStorage/sessionStorage บนเบราว์เซอร์นั้นมีความเสี่ยงจาก XSS และขาดความสามารถในการเพิกถอนสิทธิ์ (Revocation) ได้ทันที ซึ่ง session cookie แบบดั้งเดิมทำได้ง่ายกว่ามาก
  • การใช้งานในระบบหลังบ้าน (Service-to-Service): สมาชิกหลายคนแย้งว่า JWT มีประโยชน์อย่างมหาศาลและปลอดภัยมากสำหรับการสื่อสารระหว่างระบบย่อย (microservices) หรือ machine-to-machine โดยยกตัวอย่างระบบ AWS STS ที่ใช้ตรวจสอบสิทธิ์อย่างมีประสิทธิภาพ
  • มุมมองต่อตัวมาตรฐานและไลบรารี: มีการวิเคราะห์ว่าข้อผิดพลาดในอดีต (เช่น Downgrade Attacks) มักเกิดจากไลบรารีที่ค่าเริ่มต้นไม่ปลอดภัย แต่ในปัจจุบันได้รับการแก้ไขและอุดช่องโหว่เรียบร้อยแล้ว แม้ผู้เชี่ยวชาญบางส่วนจะยังวิจารณ์การออกแบบมาตรฐานดั้งเดิมว่าไม่รัดกุมพอก็ตาม

TimescaleDB สามารถบีบอัดข้อมูลอนุกรมเวลาได้สูงสุดถึง 98% ซึ่งเป็นความสามารถที่สำคัญสำหรับระบบที่มีปริมาณข้อมูลมหาศาลและจำเป็นต้องเก็บรักษาข้อมูลไว้เป็นเวลานาน โดยมีจุดเด่นและกลไกการทำงานดังนี้ครับ:

  • การออกแบบที่ต่างจากฐานข้อมูลทั่วไป: ต่างจากระบบ OLTP และกลไก TOAST ของ PostgreSQL ที่ออกแบบมาเพื่อย่อข้อมูลขนาดใหญ่แบบทีละค่า (เช่น JSONB, Text ยาว ๆ) แต่ TimescaleDB เน้นการบีบอัดรูปแบบข้อมูลข้ามแถว (Cross-row patterns) โดยบีบอัดข้อมูลอนุกรมเวลาได้ดีกว่าถึง 10-100 เท่า
  • เอนจิน Hypercore แบบไฮบริด: ใช้กลไกจัดเก็บข้อมูลแบบผสมผสาน (Row-Columnar) โดยข้อมูลใหม่จะถูกบันทึกเป็นแบบแถว (Row-based) เพื่อการเขียนและอัปเดตข้อมูลที่รวดเร็ว จากนั้นระบบจะแปลงข้อมูลเก่าให้เป็นแบบคอลัมน์ (Columnar format) และทำการบีบอัดโดยอัตโนมัติ ซึ่งช่วยเพิ่มความเร็วในการสืบค้นข้อมูลเชิงวิเคราะห์
  • การบีบอัดระดับคอลัมน์: ข้อมูลแต่ละส่วนจะถูกจัดกลุ่มเป็นบล็อกสูงสุด 1,000 แถว และบีบอัดตามประเภทข้อมูลที่แตกต่างกัน ได้แก่:
    • ตัวเลขและเวลา (Integers/Timestamps): ใช้การเข้ารหัสแบบ Delta, Delta-of-delta, Simple-8b และ Run-Length Encoding (RLE) โดยหากค่าเวลามีช่วงสม่ำเสมอ ค่า Delta-of-delta จะเป็น 0 ทำให้ใช้พื้นที่จัดเก็บน้อยมาก
    • ข้อมูลที่มีการซ้ำซ้อนสูง (เช่น machine_id): ใช้ระบบ Run-Length Encoding (RLE) เพื่อลดความซ้ำซ้อนอย่างมหาศาล
    • ข้อมูลทศนิยม (Floats): ใช้การบีบอัดแบบ XOR ตามแนวทางอัลกอริทึม Gorilla ของ Facebook เพื่อลดขนาดบิตหลัก
    • ข้อมูล JSONB และอื่น ๆ: ใช้ระบบ Dictionary ร่วมกับกลไกบีบอัดดั้งเดิม
  • พารามิเตอร์ที่ต้องใส่ใจ: ผู้ใช้งานต้องกำหนดพารามิเตอร์ segmentby (แบ่งกลุ่มตามฟิลด์เฉพาะ เช่น รหัสเครื่อง) และ orderby (เรียงลำดับเวลาเพื่อให้เก็บค่าต่างได้คุ้มค่า) ซึ่งช่วยให้ตัวประมวลผลคำสั่งสามารถข้ามบล็อกที่ไม่ตรงกับเงื่อนไขได้เลยโดยไม่ต้องอ่านดิสก์
  • ประสิทธิภาพการสืบค้น: การบีบอัดทำให้ปริมาณข้อมูล I/O ลดลง 10-20 เท่า ส่งผลให้คำสั่งสืบค้นทั่วไป เช่น การหาค่าเฉลี่ยหรือยอดรวมตามช่วงเวลา ทำงานได้เร็วขึ้นอย่างมาก

  • ความขัดแย้งของเป้าหมายทางธุรกิจและการโฆษณา: นักพัฒนาสังเกตเห็นความย้อนแย้งที่ด้านหนึ่งบริษัท AI โฆษณาขายลูกค้าระดับองค์กรว่า AI จะมาทดแทนมนุษย์และลดค่าใช้จ่ายพนักงาน แต่อีกด้านกลับต้องลงเงินหลายล้านดอลลาร์เพื่อจ่ายให้คนมานั่งสอนองค์กรการกุศลให้ใช้ AI
  • ความท้าทายในระดับทักษะ: มีข้อถกเถียงว่าหาก AI เป็นเรื่องง่ายจริง คงไม่มีความจำเป็นต้องสร้างหลักสูตรส่งคนไปประกบองค์กรเป็นปี ๆ ทั้งนี้สมาชิกหลายคนยืนยันว่าการประยุกต์ใช้โมเดลในระดับอุตสาหกรรมหรือองค์กรจริงมีความซับซ้อนสูงมากในการเชื่อมฐานข้อมูลและระบบการทำงานให้ปลอดภัยและยั่งยืน

Microsoft turns to AWS as GitHub faces AI capacity crunch

ไมโครซอฟท์เตรียมหันไปพึ่งพาบริการระบบคลาวด์ AWS ของอเมซอน หลังระบบ GitHub เผชิญวิกฤตความสามารถในการรองรับปริมาณการทำงานของ AI ที่เติบโตอย่างก้าวกระโดดครับ

💬 สรุปประเด็นเสวนาในกระทู้

การเคลื่อนไหวของยักษ์ใหญ่นี้ได้รับความสนใจจากกลุ่มวิศวกรซอฟต์แวร์เป็นจำนวนมากพร้อมความคิดเห็นที่น่าประเด็นดังนี้ครับ:

  • สถิติตัวเลขที่พุ่งทะยานจาก AI: ข้อมูลระบุว่าปริมาณการ Commit ซอร์สโค้ดบน GitHub คาดว่าจะพุ่งไปถึง 14,000 ล้านครั้งในปี 2026 เพิ่มขึ้นถึง 14 เท่าจากสถิติ 1,000 ล้านครั้งในปี 2025 ซึ่งเป็นผลมาจากระบบ AI และผู้ช่วยเขียนโค้ดที่สั่งบันทึกการทำงานอย่างรวดเร็วถี่ถ้วน
  • พฤติกรรมการเขียนโค้ดที่เปลี่ยนไป: นักพัฒนาอธิบายว่าการใช้งาน AI ทำงานทำให้ต้อง Commit ข้อมูลถี่ยิบเพื่อเป็นจุดบันทึกความปลอดภัย (Checkpoint) ป้องกันไม่ให้ AI ทำโค้ดเสียหายหรือสูญหายระหว่างรันคำสั่ง นอกจากนี้ปริมาณ Commit มหาศาลยังสร้างภาระผูกพันอย่างรุนแรงต่อระบบ CI/CD, การคำนวณ diff ของ PR และการจัดเก็บฐานข้อมูล
  • ปัญหาความเร็วของ Azure Virtual Disks: มีการแบ่งปันเกร็ดประวัติศาสตร์ว่า ผู้ร่วมก่อตั้ง GitHub เคยบอกกับผู้บริหารไมโครซอฟท์ในอดีตตั้งแต่ช่วงที่เข้าซื้อกิจการว่า ปัญหาร้ายแรงในการรัน Git บน Azure คือความเร็วของดิสก์เสมือน (IOPS) ที่ช้าเกินไปและมีราคาสูง ซึ่ง AWS ให้ประสิทธิภาพด้านดิสก์และการอ่านเขียน I/O ที่เหมาะสมกับความต้องการในการอ่านเขียนซอร์สโค้ดมหาศาลมากกว่า
  • ปัญหาจากบอทอัตโนมัติ: บอร์ดอภิปรายชี้ว่าปริมาณทราฟฟิกและภาระของระบบกว่า 1% ในปัจจุบันเกิดจากการอัปเดตเวอร์ชันไลบรารีอัตโนมัติของ Dependabot และบอทรีวิวโค้ดต่าง ๆ ซึ่งส่งคำขอเข้ามาเป็นระลอกอย่างไม่ขาดสาย
